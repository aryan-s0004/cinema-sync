  3. WHY MODULAR ARCHITECTURE (NOT JUST 2 FOLDERS)
================================================================================

  controllers/
    Thin HTTP layer only. Reads req, calls a service, sends res.
    Zero business logic - the same service is callable from tests or
    cron jobs without needing an HTTP context.

  routes/
    Maps URLs to controller methods. Stacks middleware (auth guard,
    rate limiter, validator) in the correct order. Adding auth to one
    endpoint is a one-line change here, touching nothing else.

  models/
    Mongoose schemas with indexes and virtuals. Isolated so multiple
    services import them without circular dependencies.

  services/
    ALL business logic: booking state machines, payment orchestration,
    seat locking, ticket generation. Hardest code to test - being
    isolated from HTTP makes unit tests straightforward.

  middleware/
    Cross-cutting concerns: JWT verification, request ID injection,
    rate limiting, error normalisation. Applied once at the app level,
    never copy-pasted into controllers.

  validators/
    Input schemas at the API boundary. Malformed input rejected before
    it reaches any business logic.

  utils/
    Pure stateless helpers. No imports from other internal modules.
    Safe to use anywhere without circular dependency risk.

  config/
    All env var access and validation in one place. Missing required
    key fails at boot with a clear message instead of a runtime crash.

  Why NOT just 2 folders?
    Payment logic, seat concurrency, ticket signing, email/SMS, and TMDB
    integration all change at different rates and need different test
    strategies. A bug in ticketService should not require reading payment
    code to find it. Flat structures become unmaintainable at this scope.

================================================================================
  5. BOOKING FLOW (END-TO-END)
================================================================================

  1. / -> MovieDetailPage (/movies/:movieId) -> select show time
  2. BookingPage (/booking/:showId)
     - GET /api/seats?showId=... loads seat availability map
     - User selects seats
     - POST /api/booking-intents locks them:
         Seat.status = "locked", lockedBy = userId,
         lockedUntil = now + SEAT_LOCK_MINUTES
  3. Confirm -> POST /api/bookings
     - Seats atomically moved locked -> booked via updateMany
     - Booking created: status = pending_payment,
       paymentExpiresAt = now + PAYMENT_WINDOW_MINUTES
  4. PaymentPage (/payment/:bookingId)
     - POST /api/payments/initiate
       Returns: clientSecret + publishableKey (Stripe)
             or gatewayToken + orderId (mock)
  5. User completes payment (Stripe Elements or mock OTP flow)
  6. POST /api/payments/confirm verifies payment server-side
  7. On success: booking.status -> confirmed, Ticket created, QR signed
  8. PaymentSuccessPage -> Dashboard shows booking + PDF download link


================================================================================
  6. PAYMENT FLOW (STRIPE FULL LIFECYCLE)
================================================================================

  Step 1  Client: POST /api/payments/initiate { bookingId }
  Step 2  Server creates Stripe PaymentIntent:
            amount   = (base + convenienceFee + 18% tax) x 100 paise
            currency = inr
            customer = Stripe Customer ID (created/cached on User doc)
            metadata = { bookingId, userId }
  Step 3  Server returns { clientSecret, publishableKey }
  Step 4  Client mounts <PaymentElement> with clientSecret
  Step 5  User pays -> stripe.confirmPayment() on client
  Step 6  Stripe webhook: POST /api/payments/webhook/stripe
            signature verified -> booking confirmed on payment_intent.succeeded
  Step 7  Client also polls: POST /api/payments/confirm { transactionId }
            Server calls stripe.paymentIntents.retrieve -> double-verifies
  Step 8  Both paths are idempotent (safe to call twice)

  Duplicate booking prevention:
    Seats atomically reserved BEFORE Booking document created
    Booking confirmed ONLY after server-side payment verification
    PaymentIntent reused if not expired (idempotency key tracking)
    Webhook event IDs tracked to prevent double-processing

  Seat locking approach:
    Seat.status: "available" | "locked" | "booked"
    Locked: lockedBy (userId) + lockedUntil (timestamp)
    runMaintenanceSweep() called on every non-health API request:
      releases expired locks AND expires timed-out pending bookings
    Atomic updateMany with status+lockedBy conditions prevents race condition

  10. ISSUES FOUND + FIXES APPLIED (REAL, CODE-BASED)
================================================================================

  FIX 1 - api/config/db.js: MongoDB pool size too large for serverless
  -----------------------------------------------------------------------
  File  : api/config/db.js  (committed 2026-04-10)
  Issue : maxPoolSize defaulted to 100 with Math.max(..., 20) floor.
          Each cold-start Vercel invocation could open 100 connections.
          With concurrent invocations, Atlas M0 (500 conn limit) is
          exhausted within minutes of real traffic.
  Fix   : Removed Math.max floor. New defaults:
            maxPoolSize = 5   (was: 100, with minimum enforced at 20)
            minPoolSize = 1   (was: 5)
          MONGO_MAX_POOL_SIZE env var still overrides for manual tuning.

  Before: maxPoolSize: Math.max(Number(process.env.MONGO_MAX_POOL_SIZE || 100), 20)
  After:  maxPoolSize: Number(process.env.MONGO_MAX_POOL_SIZE || 5)

  FIX 2 - api/config/db.js: process.exit(1) removed (legacy)
  -----------------------------------------------------------------------
  File  : api/config/db.js (already fixed in current api/ version)
  Issue : Old backend/config/db.js called process.exit(1) in catch block.
          In serverless, this permanently crashes the container.
  Status: ALREADY FIXED - catch block throws, api/index.js catches it
          and returns a JSON 500 response.

  FIX 3 - Serverless-incompatible setInterval for booking expiry
  -----------------------------------------------------------------------
  File  : api/app.js + api/services/bookingExpiryService.js
  Issue : Old server.js used setInterval (startBookingExpiryJob).
          In serverless, function containers are stateless - the
          interval dies when the container goes cold.
  Fix   : Replaced with runMaintenanceSweep() called on every non-health
          API request. Uses module-level lastSweepAt + sweepIntervalMs
          to throttle execution. Module state persists across warm
          invocations, making this serverless-safe.

  FIX 4 - JWT secret flexibility (single env var setup for Vercel)
  -----------------------------------------------------------------------
  File  : api/app.js (startup block at top)
  Issue : App required three separate env vars: JWT_ACCESS_SECRET,
          JWT_REFRESH_SECRET, TICKET_QR_SECRET.
  Fix   : At boot, if specific var missing but JWT_SECRET present:
            process.env.JWT_ACCESS_SECRET  = process.env.JWT_SECRET
            process.env.JWT_REFRESH_SECRET = process.env.JWT_SECRET
            process.env.TICKET_QR_SECRET   = process.env.JWT_SECRET
          One Vercel env var covers all three.

  FIX 5 - api/index.js: unhandled boot failures
  -----------------------------------------------------------------------
  File  : api/index.js
  Issue : No try/catch around boot sequence. If connectDB threw
          (e.g. MONGO_URI not set), Vercel returned a raw 502 with
          no body - impossible to debug from the browser.
  Fix   : try/catch wraps the entire boot + request handling.
          Returns clean JSON on failure:
          {"success":false,"message":"MONGO_URI is not configured","data":null}

  FIX 6 - Repo restructure: backend/ -> api/, frontend/ -> client/
  -----------------------------------------------------------------------
  Issue : Original structure (backend/ + frontend/) not compatible with
          Vercel monorepo convention. Vercel expects api/ for serverless.
  Fix   : Renamed both directories. Updated all require() paths.
          Added root vercel.json and .vercelignore.
          Updated api/package.json scripts: "dev": "vercel dev"

  FIX 7 - CORS: auto-detect Vercel preview deployment URLs
  -----------------------------------------------------------------------
  File  : api/app.js
  Issue : Old CORS only allowed CLIENT_URL. Preview deployments have
          different dynamic URLs (cinema-sync-git-branch.vercel.app),
          causing CORS to block API calls on preview links.
  Fix   : Added VERCEL_URL env detection (Vercel injects this):
            vercelOrigin = "https://" + process.env.VERCEL_URL
          allowedOrigins = CLIENT_URL union VERCEL_URL union ALLOWED_ORIGINS
